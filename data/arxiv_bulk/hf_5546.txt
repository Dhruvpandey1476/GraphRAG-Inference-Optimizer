The grammar of Golo is written using the LL(k) JJTree / JavaCC parser generator [5], mainly due to its simplicity and lack of a runtime dependency, as it generates all the Java code required for a working parser. The front-end generates an abstract syntax directly from JJTree, which is then transformed into an intermediate representation based on a Golo-specific object model, comprising classes to model reference lookups, functions, common statements and so on. The intermediate representation is visited by several phases to check for undeclared references, expand lambda functions / closures to anonymous functions, and ultimately generated JVM bytecode with the popular ASM library [6].  === Prints the following === Results: 30 -> 832040 34 -> 5702887 35 -> 9227465 38 -> 39088169 39 -> 63245986 40 -> 102334155 41 -> 165580141 42 -> 267914296  Stable bytecode, adaptive runtime dispatch. The compiler generates a largely untyped bytecode. Most references are on the java.lang.Object type, with some peculiar portions of the bytecode doing cast checks (e.g., branch conditions require refining to java.lang.Boolean and unboxing the primitive boolean value). The generated bytecode remains stable at runtime, unlike speculations and invalidations as found in Nashorn to try to take advantage of primitive types when possible.
